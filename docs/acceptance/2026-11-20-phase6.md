## How it was run

- `scripts/make_sandbox.sh` built `~/.hermes/cache/scratch/commons-sandbox` (default at the
  root, device, pikvm and pocket under `profiles/`) and a second, untouched copy for
  comparison. All four tars contain `skills/.bundled_manifest` and `skills/.hub/lock.json`,
  so bundled and hub provenance is the real one. The tars also hold each profile's real
  `config.yaml` and `SOUL.md`; the script extracts only `skills/` and writes a minimal
  `config.yaml` per profile with no `skills.create_dir`, no `skills.external_dirs` (the real
  configs listed vendor/pstack and `~/.omh` skills dirs at that time; they are left out so the
  sandbox reads nothing outside itself) and `plugins.enabled: []`. `scripts/` is not in the
  package (`packages.find include = ["commons*"]`).
- The CLI does not honour `COMMONS_HERMES_ROOT` (the plan names it; it is not implemented).
  So every command ran through a small driver (scratch only, not committed) that imports
  `commons.cli` and calls `run_command` on the real argument parser, with
  `hermes_adapter.default_root` and `state_dir` replaced by the sandbox paths, the config
  writer replaced by the core `YamlFileWriter` (the real writer runs `hermes -p NAME config
  set`, which targets the real profiles) and cron scheduling disabled. For the live run the
  writer was replaced by one that raises on any write.
- Every run was inside `bwrap` with `~/.hermes` mounted read-only except the two scratch
  folders, HOME and TMPDIR inside scratch, under the live install's venv python with `-I`
  and PyYAML from a scratch `--target` dir. Before `--apply`, every path the saved proposal
  writes (shared root, state dir, 4 config.yaml, 4 cron stores, 148 targets, 427 retired
  sources) was listed and checked: all inside the sandbox.
- `hermes_bootstrap` is not imported: with HERMES_HOME at a fresh root it prepares a whole
  Hermes runtime under that root (it wrote about 430 MB of `installs/`, `cache/` and `logs/`
  into the sandbox on the first try, and tried to take install locks under `~/.hermes`,
  which the read-only mount refused). Those folders were deleted before the real run.

are byte-identical to the moved one. This is a proposal bug: such groups need a rule (for example,
retire pristine copies equal to the kept copy, or keep the whole group local) before Phase 7.

## 6.2 merge, undo, restore

- **Merge:** `merge --next --seed variant:device` staged android-companion-apps from device's
  copy. `merge --accept` refused it and listed 12 lost lines (4 distinct lines from default,
  pikvm and pocket). After those lines were added to the staged SKILL.md, the check found
  0 lost lines, 0 problems and 0 missing references, and `merge --accept --yes` committed the
  merge, marked it resolved and moved the 4 profile copies into backup.
- **Undo:** after an edit to one shared skill was committed the way the hook does it,
  `undo agent-pipeline-forensics --yes` reverted the commit; SKILL.md sha256 is the same as
  before the edit.
- **Restore:** `restore <setup id> --yes` restored 4 config.yaml files and moved back 427
  retired copies, but android-companion-apps stayed missing from all 4 profiles. The later
  merge had retired those copies into its own backup, and the setup restore only said the
  shared copy was "new since setup and was kept". After `restore <merge id> --yes` too, the
  sandbox was byte-identical to a fresh extraction: tree_sha256 of every profile's skills dir
  and sha256 of every config.yaml match. What remains is the state dir `commons/` and the
  shared root, which restore keeps by design. Follow-up: restoring an older backup while newer
  backups exist should say so, or ask to restore those first.
